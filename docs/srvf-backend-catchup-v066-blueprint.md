## 0. 一句话结论（30 秒版）

### 2.2 Q0-B2 活动多出第五个终态 `terminated`

**这是对差看不见的坑**：openapi 的 `statusCode` description 仍只写 4 值、字典种子也没这一项，只能从源码看出来。

- `activities/utils/hook.ts` 的 `isTerminal` 判定漏了它 → 对已终止活动发全量 body 被 20030 拒，而前端文案还说成「可能已被他人发布/取消/完结」（成因说错）；

- 状态筛选下拉走 `activity_status` 字典，字典缺该项 → **既筛不出也排不掉**，需向后端要字典项或前端本地补一项（见 §8 待拍板 D2）；
- 全局搜索的状态标签同步。

### 2.3 ⚠️ 时序闸：Q0 不能提前做

`allocationModeCode` **只存在于未发版 main**。在当前 live 的 v0.66.0 上，它是**非白名单字段，发了同样 400** —— 提前补发等于把现在能用的建活动打坏。

> **Q0 必须与后端下次发版（v0.67）同一窗口上线**，不得作为「先做掉的小活」提前合并。若非要提前，只能做成按契约探测的可选发送 —— 等于前端猜后端版本，**不推荐**。
> `terminated`（Q0-B2）同属未发版增量，但它是**只读兜底**（补枚举、补状态色、放宽 `isTerminal`），提前做无害，可随 Q1 一起走。

**PR 切法**：Q0-B1 单独一个 PR，压在后端发版窗口；Q0-B2 并入 Q1。

## 6. Q4 · 带闸区（不动工，方案备查）

### 6.1 Q4-G1 结算与参与账本 —— **本轮新登记的带闸区**

**为什么带闸**：整条链在 v0.66.0 之后的未发版 main，后端 CHANGELOG 零条目、`admin-web.md` 完全未写。**未发版 = 不建 UI**（与 P6 同构理由）。

**是什么**：活动改造 v1.1 的资金语义链路，四层状态机 —— `AttendanceSettlementRun`（一活动一行，九态）→ `AttendanceSettlementVersion`（不可变提交版本，五态）→ `LedgerPostingBatch`（记账批次，五态）→ `ParticipationLedgerEntry`（append-only，DB trigger 禁 UPDATE/DELETE）。

**admin 侧恰 9 端点**（读 5 / 写 4）+ 17 个专属 BizCode + 2 个新权限码：

| 端点                                                                                | 门控码                                    |
| ----------------------------------------------------------------------------------- | ----------------------------------------- |
| `GET admin/v1/attendance-settlements`（跨活动工作台，分页）                         | `attendance.read.sheet`（**前端已在用**） |
| `GET .../{id}/review-detail`（不可变审核详情、seal、差异、缺口）                    | 同上                                      |
| `GET .../{id}/posting-batch`（账本批次进度）                                        | 同上                                      |
| `GET activities/{id}/participation-ledger`、`GET members/{id}/participation-ledger` | 同上                                      |
| `POST .../{id}/first-approve`、`first-return`                                       | `activity.settlement-first-review.record` |
| `POST .../{id}/final-approve`、`final-return`                                       | `activity.settlement-final-review.record` |

**三条关键判断（写进本文防止将来误判）**：

1. **与现有考勤单审核并存，不取代**。契约证据硬：端点删除 0、全库 deprecated 0、`attendance-sheets` 相关 DTO 零变更。「取代」只写在后端合同稿，其切换开关 `ACTIVITY_V11_WORKFLOW_ENABLED` **在后端代码里根本不存在**。→ 但后台将**同时出现两套「一审/终审」**且由同一批人行使（两个新码就 seed 在既有 `attendance-first-reviewer` / `attendance-final-reviewer` 上），两处均需加文案区分：**考勤单 = 按单据审时长分；结算 = 按活动整体审版本并入账**。
2. **admin 只能审核、造不出数**（见 Q3-2）。
3. **审核是乐观锁命令**：approve/return 各带 6 个必填快照字段 + 幂等键 → 审核抽屉必先 `GET review-detail` 再回传快照值，`operationKey` 用 `randomUUID` 并在抽屉内复用（重试幂等）；20068~20073 / 20116 统一做成「数据已变，点此刷新」而非普通报错。三方分离码 20062/20063/20064 与已有考勤三审 22074/22075 命名逐字对齐，文案可复用。
4. **`gaps` 是 200 响应体里的正常数据、用字符串 slug 不是 BizCode** → 需要第二套非数字码词典（8 个 slug 闭集，可硬编码；未知 slug 原样显示不要吞），渲染成「缺口清单」，走不通 `bizErrorMessage`。

**解冻信号**：后端把这批发版（含 `attendance-settlements` 的 tag）。
**哨兵（Q0 起常备）**：一旦本地后端跑上含结算的 main，先核 `src/views/srvf/activities-domain/attendances/` 与工作台考勤分栏是否被换契约 —— 若被换，按 P0 止血级别处理。

## 7. 反例表：**不是**落后，禁止重新立案

| 看起来像落后的东西                                                                                 | 实际                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| BizCode 前端只覆盖 86 / 后端 428                                                                   | **范畴错误**。428 里 35 个码根本没有 HTTP 出口（worker / 未接 controller）、52 个只从 App/Open 面返回；admin 面可达的新码只有 24 个。且未映射的码落地是**后端的可读中文**（`bizErrorMessage` 末行兜底 `resp.data?.message`），不会崩。正确判据是「任何新建面上线前，把该面会命中的码逐条进词条」 |
| 20144 / 20152 / 20130 / 40902 / 50001 无词条                                                       | **全部不可达**：20144 只声明在 P6 冻结端点上；20152 无生产写入方；20130 需要前端根本发不出的字段；40902/50001 是服务端并发/配置错误且未发版。不必预建                                                                                                                                            |
| `members/{id}/department` GET/PUT/DELETE 前端没有                                                  | **后端自己 deprecated 的旧面**，#146 是有据删除**不是误删**，替代面 `memberships` 在位。想显示主属部门应从 `memberships` 取 `PRIMARY` 那条，**不得重开 `/department`**                                                                                                                           |

| auth 面 16 条登录多态零覆盖                                                                        | 终点全在 `app/v1` 与招新 H5，后端原话「前端无需为此单独造页面」。**PC 后台登录链实证一字未动**：v0.65.0→HEAD 的 login / refresh / logout 三个 path 及其完整 schema 闭包**逐字节相同**                                                                                                            |

## 10. 新增便利：后端产出五 surface TS client

后端自 2026-08-13 起在 `../srvf-nest-api/docs/handoff/clients/**` 产出 admin / app / auth / system / open 五个 surface 的 TS client（`pnpm docs:feclient` 生成，CI `docs:feclient:check` 守护）。

**边界（后端刻意画得很窄）**：只有类型与调用签名，**不含 baseURL、不含令牌、不含任何鉴权逻辑**，传输层由消费方注入 `Fetcher`；**禁手改**；**字段真相仍以 live `/api/docs-json` 为准**，它只是便利派生物不是第二事实源。

**本仓建议用法（D6 倾向）**：**不引入生成物作运行时依赖**（本仓 api 层是手写 `http.request` + 中文注释的既有范式，引入会造两套风格）；接新面时**从 `clients/admin/types.ts` 拷 DTO 定义改成本仓风格**，用来保证字段零漂移。这条不改变 AGENTS.md §4「写 API 封装前先直连核对 live」的纪律。
